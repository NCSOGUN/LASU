Plan 02 · Offline access

Plan 2: Independent Node.js SMS and USSD implementation

Independent Node.js access through Africa’s Talking — with the SMS conversation, USSD menus and failure paths drawn out.

HealthAccess implementation plan · diagrams embedded as vector artwork.

Version: 1.0 · 16 November 2026

This plan follows the supplied project brief and the user's revised architecture. Read alongside Plan 1 for the shared database, authorization routines, AI contract and structured fields.

1. Architecture and meaning of offline

Node.js does not call FastAPI. It independently authenticates provider traffic, manages channel state and invokes shared PostgreSQL policy/search routines and the separate AI service. Stopping the online FastAPI deployment must not break an SMS or USSD record lookup.

Offline means the user's phone does not need mobile internet. The phone still needs cellular coverage, while Africa's Talking, Node.js, PostgreSQL and the AI service are online infrastructure. With no cellular signal, no fresh SMS/USSD request can reach the service. Do not claim cached browser content is a live offline medical record.

2. Channel feature matrix

Feature SMS USSD Later voice
General health question AI-assisted answer grounded in reviewed material Out of first-release menu; direct user to SMS Conversational
Find nearby suitable care Natural language or FIND command Guided service and location choices Spoken request
Emergency summary Patient code; minimal selected fields Patient code; selected fields, paginated Design after identity/audio review
Additional selected fields Not supported in first-release SMS Patient code + temporary code allowed for USSD Future scope
Edit profile/create grants Use online patient portal Use online patient portal Future scope

Record reads use database routines, never AI. Hospital names and contact details come from the directory. USSD menus use deterministic logic; do not wait for a model on every menu step.

3. Set up Africa's Talking

  1. Select the pilot country and mobile operators; confirm SMS/USSD availability and commercial provisioning for that market.
  2. Create sandbox applications and separate staging/production credentials.
  3. Provision a two-way SMS number/short code that can receive replies. An alphanumeric outbound sender ID alone is not a two-way conversation channel.
  4. Provision the USSD service code. Do not present a guessed code as dialable in a real network.
  5. Configure public HTTPS callback URLs for incoming SMS, SMS delivery reports, USSD requests and, if available, USSD session-end events.
  6. Confirm actual callback payloads, request-origin protections, provider timeout limits, menu-length limits, operator session duration and pricing on the provisioned service.
  7. Test with the sandbox first, then with real SIMs on the supported pilot networks and mobile data disabled.

Africa's Talking distinguishes the USSD callback URL from the session event URL; configure each for its documented purpose. See USSD go-live configuration.

Do not assume an HMAC-signature header exists. Use the origin-verification mechanism actually supported by the provisioned service, with documented network controls as applicable. Keep a non-guessable callback path as defense in depth, not as sole proof of origin. Enforce HTTPS, input size/schema limits, replay controls and rate limits. Treat the forwarded phone number as a channel identifier, not a practitioner credential.

4. Node.js modules

    middleware/      verified provider origin, validation, tracing, throttling
    channels/sms/    commands, conversation routing, message rendering
    channels/ussd/   deterministic state machine, pagination, response rendering
    services/       DB authorization adapter, matching adapter, shared AI client
    workers/        SMS processing, outbound delivery, retries, reconciliation
    repositories/   approved DB routines and telecom-owned tables
    templates/      localized prompts, errors and reviewed fallback text

A PostgreSQL-backed job queue/outbox is enough for an initial deployment. A dedicated queue can be added later without changing the contracts. Avoid a purely in-memory queue or USSD session map if multiple instances or restarts are possible.

5. Callback endpoint contracts

Node public base example: https://telecom.example.org. The domain is a placeholder.

Endpoint Purpose Response
POST /callbacks/africastalking/sms/inbound Validate and durably record incoming SMS; schedule processing HTTP 200 only after durable acceptance; no AI work in callback
POST /callbacks/africastalking/sms/delivery Apply idempotent delivery-status updates HTTP 200 after durable acceptance
POST /callbacks/africastalking/ussd Process one current USSD input/state transition HTTP 200, text/plain, starts with CON or END
POST /callbacks/africastalking/ussd/events Session-ended metadata if enabled HTTP 200 after durable acceptance
GET /health/live Process liveness Minimal response
GET /health/ready Database/queue readiness Minimal response; restrict detailed diagnostics

Example incoming SMS fields to map after checking provider fixtures:

json
{
  "id": "AT_PROVIDER_MESSAGE_ID",
  "from": "+2348000000000",
  "to": "PROVISIONED_SHORT_CODE",
  "text": "FIND child health near Ikeja",
  "date": "PROVIDER_TIMESTAMP"
}

Provider callbacks may be form-encoded rather than JSON. Normalize once at the callback boundary. Do not depend on the provider timestamp to order authorization changes. Never send the answer as the inbound webhook's HTTP body; replies are separate outbound SMS requests.

Example USSD callback fields:

json
{
  "sessionId": "AT_SESSION_ID",
  "serviceCode": "PROVISIONED_USSD_CODE",
  "phoneNumber": "+2348000000000",
  "text": "1*2*Ikeja"
}

Africa's Talking's USSD interface uses a continuing CON or terminating END text response. See the provider's USSD tutorial. Verify the exact fields and limits against current provisioned-service fixtures before deployment.

USSD text represents the cumulative input path in the expected integration. Parse the path, validate it against the stored session and process only the next valid transition. Never treat the full string as a fresh answer, and never log or persist the raw cumulative string: it can contain access codes. networkCode and other metadata are optional until confirmed by your actual provider contract.

6. SMS workflow — hospital recommendation

Example, using fictional hospital data:

text
User: I need a hospital for my child.
HealthAccess: Which area or nearby landmark are you in?
User: Ikeja.
HealthAccess: Demo Community Hospital — child health.
12 Example Road, Ikeja. Approx. 2.4 km from area centre.
Contact not listed. Reply MORE for another option.

The prototype's facilities and distances are illustrative. In production, populate this message only from actual directory records. If a number is available, include it; otherwise state it is not listed. The recommendation is not an appointment or real-time confirmation that a clinician is present.

SMS commands and state

Input Handling
HELP Show brief available commands, supported language options and relevant channel notice
FIND <care> near <area> Resolve service/location, then deterministic facility matching
Natural-language care request Shared AI interpretation, validated into the same search flow
ASK <health question> Reviewed-content retrieval and AI-assisted general answer
LOOKUP <patient code> Emergency-summary routine only; no AI
MORE Next stored result, only when a non-expired referral conversation exists
CANCEL Cancel pending clarification and clear transient state
STOP End current interaction and record opt-out where applicable; distinguish unsolicited messaging from future user-initiated requests

Store idle, awaiting_service, awaiting_area, awaiting_area_choice, awaiting_profile_confirmation, showing_results and closed as explicit states. A configurable 15-minute clarification window is a proposed starting point. Expired conversations start a new request instead of interpreting a reply against stale health context.

Optional personalized matching

Default guest SMS/USSD requests use only the request and current location. Never load a full profile just because the sender's phone matches an account.

To enable personalization:

  1. Patient signs into the online portal and verifies the phone link.
  2. Patient explicitly opts in for the chosen channel, exact profile fields and an expiry.
  3. Node finds an active link and consent but still asks for confirmation for this search without disclosing the fields.
  4. On confirmation, the shared DB policy returns only the permitted matching context.
  5. Node applies reviewed local matching rules and records which scope was used.
  6. Revoking consent or unlinking a phone immediately prevents subsequent profile use.

This consent does not authorize sending profile details in an SMS or granting record access to a practitioner. Reverify phone linkage after account recovery/change and expire stale links. First build guest matching; add this optional flow after linking and revocation are working.

7. SMS workflow — emergency summary

Examples:

text
Success: Emergency summary: Allergy: Penicillin. Contact name: Chika.
          (Only patient-selected information.)

Unavailable: No shared summary is available for that code. Check the code.

Both are demonstration strings. Unselected contact phone, medication, date of birth and other fields must not leak into the message. An empty summary is a valid patient choice. Avoid responses that reveal whether an unknown or non-sharing patient exists.

For queued record replies, resolve the current authorized projection immediately before dispatch. A selection change between receipt and send must be respected where the message has not yet been handed to the provider. Delivered SMS cannot be recalled. Temporary-code unlocks are not a first-release SMS feature; redirect the user to USSD or the practitioner portal rather than forward additional details.

8. SMS workflow — general health question

  1. Callback stores the message and acknowledges quickly.
  2. Worker runs reviewed urgency rules first.
  3. For supported general information, Node calls the shared AI service directly.
  4. AI service retrieves approved material and returns an answer with content version/IDs.
  5. Node validates output, removes unsupported actions and formats a short response.
  6. If no reviewed material supports the response, send a reviewed fallback or offer to find professional care.
  7. Create an outbound job and track provider acceptance and delivery independently.

The AI has no database credentials for unrestricted patient records and receives no patient or temporary access codes. Apply prompt/data minimization and provider settings before sending real health information. Make the AI-assisted nature of the channel clear in onboarding/help. Urgent guidance must not wait for a model call or a location clarification.

Split long messages deliberately, respecting the provider's actual encoding and segment rules. Unicode can change segmentation and cost. Keep one clear follow-up per turn; do not blindly truncate clinically important text mid-sentence.

9. USSD: complete menu flow

Dial the provisioned service code. First response:

text
CON HealthAccess
1. Find nearby care
2. Emergency summary
3. View shared details
0. Exit

Option 1 — Find nearby care

Only send the hospital's public directory details by SMS after the user's selection. This action does not send the patient's records. If SMS send is queued, say “SMS requested”, not “delivered”. If no matching hospital exists, offer another area or a wider search. Do not substitute an unsuitable hospital solely because it is close.

Option 2 — Emergency summary

No login is required for this limited public-by-code summary, as specified in the brief. Do not silently require a practitioner account for this flow.

Option 3 — Additional shared details

USSD uses the two-code bearer grant permitted by the brief; it does not claim to authenticate the recipient as a practitioner. The patient sees this channel choice while issuing the grant. The online practitioner route additionally requires an approved practitioner account. Both channels enforce the same field scope, expiry, revocation and read-only rules.

Do not automatically send unlocked additional details to SMS. A grant valid for web access only must fail on USSD.

10. USSD state-machine implementation

State Expected input Next state / action
MAIN 1, 2, 3 or 0 Care, emergency-code entry, granted-code entry or end
CARE_SERVICE Valid service menu number CARE_LOCATION
CARE_LOCATION Bounded area/landmark text CARE_AREA_CHOICE or results
CARE_AREA_CHOICE Valid offered choice Resolve area; optional consent step; results
CARE_PROFILE_CONFIRM Explicit yes/no Search with or without permitted profile context
CARE_RESULTS Next, send SMS or exit Another result, one idempotent delivery job or end
EMERGENCY_CODE Patient code Authorized summary or generic failure
GRANT_PATIENT_CODE Patient code GRANT_ACCESS_CODE
GRANT_ACCESS_CODE Temporary code Authorized read session or generic failure
RECORD_PAGE Next/back/exit Revalidate grant and current field scope before pagination
END None No further transition for this session

Implementation pattern:

Repeated callbacks must not create another grant session, advance another page or send another SMS. Replaying a cached protected response must not bypass current expiry/revocation checks; recompute protected projections when necessary. Don't retain a last-response cache containing medical data longer than the session, and protect it if retained.

Proposed initial callback performance target: application processing p95 under one second for deterministic menus. This is a development target, not a claimed provider timeout. Set hard service/database timeouts below the provisioned operator deadline. Session idle expiry must be no longer than the applicable carrier limits. Clear transient code material on completion/timeout. Use configurable menu-length and field-count limits; long records need pagination.

Invalid input should repeat the current prompt with a short correction. After a bounded number of invalid attempts, end the session. Code guessing needs limits across sessions too, by phone, IP/provider context, target digest and aggregate traffic. Avoid a permanent target lockout that lets strangers deny access to a patient's public summary.

11. Telecom tables in shared PostgreSQL

Table Important columns / constraints
telecom.channel_links id PK, patient_id FK, encrypted E.164 phone, phone lookup digest, verified time, expiry, revoked time; unique active binding according to account policy
telecom.sms_inbox id PK, provider, provider message ID, encrypted sender/body where required, received time, processing state, attempts; unique (provider, provider_message_id)
telecom.sms_conversations id PK, phone digest, state, resolved service/area IDs, permitted-consent reference, result IDs, expiry, version
telecom.ussd_sessions id PK, provider session ID, phone digest, service code, state, sanitized context, read-session reference, input fingerprint, version, expiry; unique (provider, provider_session_id)
telecom.outbox id PK, unique logical job key, recipient reference, payload or render reference, source event, status, attempt count, next attempt time, claim lease, provider message ID, expiry
telecom.delivery_events id PK, provider message ID, provider status, received time, event fingerprint; unique fingerprint for duplicate reports
telecom.channel_preferences phone digest, optional language, opt-out scope, updated time

Use the core tables in Plan 1 for patient data, grants, facility matches, consent and access audit. Do not create a telecom copy of patients or emergency summaries. The Node database role writes telecom tables and approved audits; record access goes through the shared restricted routines.

For callback-derived data, retain the minimum needed. Suggested pilot defaults: purge USSD transient state soon after expiry; keep encrypted inbound message bodies only for a short operational window such as seven days, subject to the agreed retention policy; keep delivery metadata separately from health text. These are proposed defaults to confirm for the deployment, not legal retention claims. Avoid plaintext full request/response logging at reverse proxies, tracing middleware or provider-debug export jobs.

12. Reliable SMS sending

  1. Insert the accepted inbound event and processing job atomically; acknowledge only when durable.
  2. Worker claims jobs with a lease so multiple instances cannot process one job concurrently.
  3. A completed logical action creates one uniquely keyed outbox job.
  4. Sender renders/revalidates any time-sensitive permitted content, calls Africa's Talking and stores the provider message ID.
  5. Track queued, sending, accepted, delivered, failed, unknown and expired separately.
  6. Delivery callback reconciles provider status idempotently. A provider report can arrive before the send response has been persisted; retain unmatched reports temporarily and reconcile them later.
  7. Retry known transient failures with bounded exponential backoff. Permanent failures go to a review/dead-letter state.
  8. A network timeout after sending may mean the provider accepted the message. Mark it unknown and reconcile before resending; application-level deduplication alone cannot guarantee exactly-once delivery through a remote provider.

Africa's Talking documents retrying incoming SMS callbacks until successful acknowledgement, which is why durable acceptance and duplicate handling matter. Verify the current retry behavior for the account. See incoming SMS callbacks.

13. Failure behavior

Failure User experience Implementation response
Ambiguous location Ask one short question with choices Do not guess precise coordinates
No suitable hospital Offer another area or wider radius Keep result empty; do not invent a facility
AI unavailable Explain temporary limit; offer service menu/command Keep record lookup and directory search operational
FastAPI unavailable Offline functions continue No Node → FastAPI dependency
PostgreSQL unavailable Brief unavailable message No cached protected record fallback; avoid false success
USSD timeout Redial starts a fresh session Clear transient access context
Invalid/expired/revoked code Generic unavailable message Audit outcome without exposing record existence/values
SMS accepted but no delivery report Do not claim delivery Keep pending/unknown state and reconcile
Repeated callback Same safe logical outcome No duplicate state transition or outbox job
Consent withdrawn Subsequent personalization/record reads denied as applicable Check live scope at use; existing delivered SMS cannot be recalled
Phone has no cellular coverage No fresh interaction can occur No promise of zero-signal access

14. Later voice workflow

Confirm bidirectional audio, supported streaming or turn-based modes, interruption handling, language support, caller costs and consent before implementation. Do not assume that providing a voice webhook establishes real-time AI audio capability. Keep voice behind a feature flag and outside the first SMS/USSD acceptance criteria.

15. Implementation order and demonstration

Milestone Build Acceptance condition
1 — Provider boundary Callback validation, fixtures, inbox/outbox and session storage Duplicate callback causes one logical job; origin failures are rejected
2 — Deterministic SMS HELP, FIND, LOOKUP, location clarification and matching SMS works with FastAPI stopped and AI disabled for command-based flows
3 — USSD All three menu paths, paging, invalid input and timeout No raw codes in logs; extra fields need valid USSD scope

Demo script:

  1. Use a fictional patient and explicitly select only allergies and emergency contact name for public sharing.
  2. In the portal, save the emergency summary.
  3. With mobile data off, retrieve it through USSD. Confirm medication and date of birth are absent.
  4. Create a temporary code for medications, permitted on USSD, and unlock exactly that field with both codes.
  5. Revoke the code online; another USSD read/page request must fail.
  6. Text a child-health care request without an area; receive a clarification.
  7. Reply with a known area; receive a matching seeded hospital and its address.
  8. Stop FastAPI and repeat an offline lookup/search successfully.
  9. Stop the AI service and repeat emergency lookup and structured FIND successfully.
  10. Replay the same SMS callback and the same USSD input; verify no duplicate outgoing SMS or extra transition.

The standalone HTML includes a local simulation of these interactions for design review. It does not send SMS, dial USSD or connect to any backend.
